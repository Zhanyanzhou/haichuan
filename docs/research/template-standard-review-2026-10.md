# 店铺装修模板规则审查报告（2026-10）

> 审查日期：2026-10-12。
> **本文件是审查记录，不是产品规则。** 2026-10-12 用户采纳其中的七项推荐，决定见 [D.41](../DECISIONS.md)，生效规则见[区块模板标准](../page-builder/section-template-standard.md)。下文保留审查当时的问题描述。
> 官方依据见[官方资料研究记录](template-standard-official-sources-2026-10.md)。本次只改文档，不改合同和代码；合同与代码差距列在附录 A，后续需单独授权。

## 0. 结论先行

现行规则的问题不在于“写得不够多”，而在于**写错了重点**：

1. 所谓“模板标准”大部分在讲创建向导和编辑器怎么操作（七步、精调、保存），真正决定一节好不好的**区块规格**（这一节必须有什么、最多多少字、图片多大、手机怎么变、空了怎么办、怎么验收）反而又薄又散。
2. 第三层“受控变化”自带一套圆角、间距、边距和风格数值，与 UI_GUIDE 的令牌并行，等于在模板里另立了一个小设计系统。
3. 文档写的不变量，机器合同大多不拦：任意十六进制颜色、字重 100～900、最小字号 8px、省略号截断、拉伸变形、页面实例改坐标，合同都允许。
4. 响应式只在 768px 切一刀，竖屏平板、横屏手机和超宽屏都没有专门规则，验收矩阵也不覆盖它们。
5. 没有量化验收（字数、图片、性能、无障碍压力测试），也没有版本兼容规则。

**保留的部分**（这些是对的，草案继承）：

- 四层内容不混用（store-decoration §3）、页面锁定精确模板版本并显式升级（D.38）、页面模式只编辑合同开放的实例内容（D.17）、整页成篇与“一块模板是一节”（store-decoration §4）。
- 九个区块角色作为第二层（只是命名和归属需要整理）。
- 字号只认 UI_GUIDE §2.3、色值只认 UI_GUIDE §4.1。
- 只有第一个可见主视觉获得 h1 与首图优先（D.31）。
- 非法输入保留并就近报错、不静默夹取（template-creation-rules §3、§9.3）。

## 1. 严重程度定义

| 级别 | 含义 |
| --- | --- |
| 高 | 会直接产出不合格的公开页面，或规则之间互相矛盾导致无法判定对错 |
| 中 | 规则缺口会让同类问题反复出现，但目前有人工把关可以拦住 |
| 低 | 表述、归属或组织问题，增加维护成本 |

## 2. 问题清单

### 问题 1（高）：标准的重心是向导流程，不是区块规格

| 项 | 内容 |
| --- | --- |
| 原位置 | template-creation-rules §1～§10 以“步骤 1～7”和编辑器功能组织；区块规格散落在 template-creation-rules §2 表格（只有“推荐画幅 / 布局 / 图片 / 内容”四列）、launch-template-set §3（M1～M7 骨架）和 store-decoration §2（页面与角色对照） |
| 依据 | Shopify 每个 section 用 schema 统一声明 `name`、`limit`、`settings`、`blocks`、`max_blocks`、`presets`、`enabled_on`，主题商店还要求默认值演示用法、内容变化时布局仍有意为之（研究记录 §1） |
| 影响 | 同一个角色要翻三份文档才能拼出规格；而且拼出来仍然缺字数上限、手机比例、最小像素、空态、首图策略、标题层级和验收条件。审稿人无法判断“这一块合不合格” |
| 改法 | 草案 §3 用统一的“角色规格卡”给九个角色逐一定义：用途、页面准入、每页上限、必填与可选槽位、字数、双端比例与最小像素、焦点与安全区、变体、可开放设置、标题层级、行动策略、空态、首图策略、禁区、验收。向导降为从属（草案 §13）：每一步的选项都从规格卡过滤 |
| 需要决策 | 否（结构调整） |

### 问题 2（高）：第三层预设是一套平行令牌，风格名称无法判定

| 项 | 内容 |
| --- | --- |
| 原位置 | template-creation-rules §7.1 风格（简约 / 高端 / 温暖 / 极简）；§7.3 圆角 0/8/16/24/32、间距 12/16/24/32 与区域 24/32/48/64、内容边距为画布短边的 4%/6%/8%；§5 图片圆角默认 24px |
| 依据 | UI_GUIDE §6.5“运行时色值、字体、间距、圆角……必须由现有全局设计令牌或组件实现，页面内硬编码不成为新标准”；UI_GUIDE §3.2 前台间距只用 24/32/48/64/80/96，8/12/16 标为“前台 —”；UI_GUIDE §6.3 产品卡默认无大圆角；Shopify 主题商店明确“只改间距、颜色、字体、圆角属于表面变化”；DTCG 与 Material 3 都要求组件引用令牌别名而不是原始值（研究记录 §1.3、§6） |
| 影响 | ① 模板默认产出 16px、24px 圆角照片，与珠宝品牌惯用的直角编辑影像相反；② 基础间距 12/16 在前台没有用途；③ 内容边距按画布短边计算，桌面 1440×810 的“标准 6%”约 49px，偏离 UI_GUIDE 桌面边距 80px，手机随内容增长时短边是宽度，边距约 23px，也与 20px 不一致；④ “简约”和“极简”只差“中等圆角”，“高端”与“极简”的参数组合完全相同（template-creation-rules §7.1 表 2），名字无法区分，也无法验收；⑤ template-creation-rules §7.2 说“风格只改变密度、圆角和对齐”，§7.1 表又让风格决定配色 |
| 改法 | 草案 §2.3：第三层只允许引用 UI_GUIDE 令牌，不写原始像素；间距、边距只取 UI_GUIDE §3.2 前台档位与 §3.5 边距；圆角默认 0，非零只在有理由的局部（如圆形头像）使用；四个风格名改为两个可判定的维度：**留白密度**（标准 / 宽松）与**影像权重**（影像主导 / 图文均衡 / 文字主导） |
| 需要决策 | **是**（待决事项 5：取消四个风格名；圆角默认改为 0 属于其中一部分） |

### 问题 3（高）：机器合同不执行文档里的不变量

| 项 | 内容 |
| --- | --- |
| 原位置 | `contracts/page-builder/template-definition.schema.json`：`slotRules.color` 接受任意十六进制；`fontWeight` 允许 100～900；`instanceEditPolicy.minFontSizePx` 最低 8；`overflow` 允许 `clip` / `ellipsis`；`objectFit` 允许 `fill`；`instanceEditPolicy` 允许页面改 position / size / zIndex；`length` 只有单值，表达不了 `clamp()`；`fontRole` 只有 display / heading / body / caption / action 五种，与 UI_GUIDE §2.3 六个层级对不上；存在 `backgroundGradient` |
| 依据 | UI_GUIDE §2.4 前台标题 300～500；UI_GUIDE §2.3 下限“不得低于该层级在本表的手机取值”（最小 11px）；UI_GUIDE §4.1 色值底盘；WCAG 1.4.12 固定高度文字容器会失败、截断会丢内容；web.dev `object-fit` 只建议 cover / contain（研究记录 §3、§4） |
| 影响 | 文档说“不允许”，合同说“合法”，渲染器照单全收。审查只能靠人眼，CI 拦不住。launch-template-set §2.1 自己也承认“机器允许的比本文允许的更宽” |
| 改法 | 草案 §2.4 列出“文档不变量 → 合同字段”的对照表，并把每条标为“合同已执行 / 需收紧”。收紧本身属于合同变更，列入附录 A，不在本轮执行 |
| 需要决策 | 否（但实施需单独授权） |

### 问题 4（高）：槽位缺少基础能力：替代文本、手机图源、安全区、视频

| 项 | 内容 |
| --- | --- |
| 原位置 | 合同 slot 只有 `required / editable / hideable / emptyPolicy / validation`；`validation` 没有替代文本规则。Renderer（`DynamicTemplateRenderer.tsx` 第 591～592 行）读取页面内容里的 `alt`，**缺失时静默变成空 alt**，即被当成装饰图。图片内容只有一个 `src`，手机覆盖只能改节点背景图，图片槽位没有独立手机图源。槽位类型没有 video。`maxLines` 用 line-clamp 隐藏超出的文字（第 572～577 行） |
| 依据 | WCAG 1.1.1：装饰图必须是显式判断；Shopify `image_picker` 自带 alt 与焦点；web.dev `<picture>` 用于构图换片，alt 要同时适用两种裁切；Shopify 与 web.dev 的视频规则（poster、静音、可暂停、字幕）（研究记录 §1.2、§3、§4） |
| 影响 | 运营漏填 alt 时没有任何提示，读屏用户直接丢失信息；首屏手机竖图只能靠裁切同一张横图或用背景图实现，而背景图又违背“主视觉不要用 CSS 背景图”的性能建议；video-story 角色有名无实；长文字被悄悄截断 |
| 改法 | 草案 §4：图片槽位必须声明“信息图 / 装饰图”，信息图的 alt 必填，空 alt 只能由“装饰图”开关产生；首个可见主视觉允许“桌面图 + 手机图”双源，用 `<picture>` 输出；焦点与文字安全区作为槽位属性；视频槽位单列规则；文字溢出一律换行，`maxLines` 只作为编辑期警告阈值，不再在公开页截断 |
| 需要决策 | 否（但实施需单独授权） |

### 问题 5（高）：响应式只在 768px 切一刀，风险宽度没有规则也不验收

| 项 | 内容 |
| --- | --- |
| 原位置 | D.16、D.36；template-creation-rules §3.1（第 160、181、182 行）；UI_GUIDE §3.5；store-decoration §4（第 146 行）；PB-RESP-002 只验 390/768/1024/1280/1440/1920 |
| 依据 | Material 3 把 600～839 定为 Medium（竖屏平板，建议单栏），768 正落在区间内部；Android 把高度 <480dp 定为 Compact height（99.78% 的横屏手机），并指出宽 Medium、高 Compact 时双栏不实际；项目自己的竞品观察显示三家首屏竖向素材延续到 1024～1280；超宽屏没有最大内容宽度与首屏高度上限（研究记录 §5） |
| 影响 | ① 768～1023 的竖屏平板会拿到桌面 16:9 叠字首屏和左右双栏，文字栏可能不足 300px；② 横屏手机（约 844×390）进入桌面内容，16:9 首屏高约 475px，加上页头后主体与文字容易被裁；③ 2560 宽时 16:9 首屏高 1440px，远超一屏；④ 320 宽（WCAG 重排基准）不在矩阵里 |
| 改法 | 草案 §6：**保留两个内容端点**（不新增平板稿），但新增“几何档位”与“高度感知”规则：首屏高度上限为 `min(比例高度, 100svh − 页头高度)`；横屏矮视口（高 <480）首屏改为文字在图下或降低比例；600～1023 宽时分栏按最小文字栏宽自动转为上下；超宽屏设最大内容宽度与首屏最大高度。验收矩阵扩到 320、390、600、767、768、834、844×390、1024、1280、1440、1920、2560 |
| 需要决策 | **是**（待决事项 1：方案 A 把内容端点移到 1024；方案 B 保留 768 并加上述规则。研究倾向方案 B） |

### 问题 6（中）：角色分类口径不一致，存在重叠与缺口

| 项 | 内容 |
| --- | --- |
| 原位置 | store-decoration §2 九角色；template-creation-rules §2；launch-template-set §1、§3 |
| 依据 | Shopify 用 preset 表达同一 section 的不同布局，而不是为每种布局新建 section（研究记录 §1.1、§7） |
| 影响 | ① 角色名混用两种口径：`collection-story`、`craft-detail`、`maison-fact` 按用途命名，`editorial-split`、`creation-grid` 按布局命名，`editorial-split` 又被用来讲工艺、人物和品牌，与 craft-detail、maison-fact 的用途重叠；② `editorial-media`（大图、弱文字、全幅背景）与 `page-hero` 的全幅变体在结构上几乎一样，区别只是在页面上的位置，而位置本来就不该写进模板（store-decoration §4“模板定义不记录我是第几节”）；③ 缺少的常见节：单件作品聚焦（一件作品 + 工艺说明）、定制流程步骤（/custom 的核心）、纯文字引言（/catalog 用 M1 的“克制变体”凑合） |
| 改法 | 草案 §3.1 给出建议分类：角色一律按用途命名，布局作为角色内的变体；把 editorial-media 并入 page-hero 的“非首屏影像章节”变体；新增三个候选角色。这些改名和增删影响合同枚举与已有模板，只列为建议 |
| 需要决策 | **是**（待决事项 2） |

### 问题 7（高）：没有量化验收

| 项 | 内容 |
| --- | --- |
| 原位置 | template-creation-rules §11、store-decoration §7、launch-template-set §7 的验收条目都是定性描述（如“长文本换行、行高、最大字数和溢出反馈仍须验收”，但没有给出最大字数） |
| 依据 | Shopify 主题商店：Lighthouse 性能均分 ≥60、无障碍 ≥90，并要求用真实内容测试；web.dev：LCP ≤2.5s、CLS ≤0.1、INP ≤200ms；WCAG 1.4.4（200%）、1.4.10（320px）、1.4.12（文字间距）（研究记录 §1.3、§3、§4） |
| 影响 | “合格”只能靠主观判断；同一模板不同人审出不同结论；没有图片数量与体积上限，首页可能叠出十几张大图 |
| 改法 | 草案 §8 给出媒体与性能预算，§9 给出 WCAG 2.2 AA 映射，§12 给出压力矩阵（极短、极长、缺图、满额、200%、320px、文字间距）与每项阈值 |
| 需要决策 | 否；具体预算数值在草案里标为“建议初值”，待实测后再定 |

### 问题 8（中）：没有版本兼容与破坏性变更规则

| 项 | 内容 |
| --- | --- |
| 原位置 | template-creation-rules §9.1 只说“新版本不改写已锁定的旧页面”；没有说哪些改动算破坏性、槽位 key 能不能改、旧页面如何升级 |
| 依据 | Puck：重命名或删除 prop 属于破坏性变更，用渲染端兼容或 `transformProps` 迁移，转换要容忍新旧数据并存；Shopify：不要依赖 block id 字面值（研究记录 §1.1、§2） |
| 影响 | 改一个槽位 key 会让已锁定该模板的页面在升级时静默丢内容；运营在“升级到新版”时看不到会丢什么 |
| 改法 | 草案 §11：变更分为兼容 / 需迁移 / 破坏性三级；发布后的槽位 key 不可改、不可复用；删除或改类型必须附迁移转换和升级差异预览 |
| 需要决策 | 否 |
