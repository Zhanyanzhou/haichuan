# 管理后台中文文案规范 V4

> 适用范围：管理后台的菜单、页面标题、表单、列表、状态、反馈与确认文案。后台以清晰、效率、状态准确和低误操作为目标，不使用客户前台的品牌宣传语气。
>
> 排版、字号、行高、间距、控件密度、色彩对比和响应式数值只以 `docs/UI_GUIDE.md` 的“附录 A · 管理后台排版、密度与无障碍”为准；本文不复制第二套视觉数值。

## 1. 基本原则

1. **先说对象，再说动作**：页面名使用稳定名词，如“商品管理”“订单详情”；按钮使用明确动词，如“新建商品”“保存修改”。
2. **一个动作只用一个主词**：同一层级不混用“新建/新增/创建”“编辑/修改”“删除/移除”。
3. **状态描述事实，按钮描述动作**：状态写“已启用”，按钮写“停用”；状态写“已发布”，按钮写“取消发布”。
4. **错误必须可行动**：采用“发生了什么 + 下一步怎么做”，例如“商品加载失败。请稍后重试。”
5. **不改写业务含义**：订单、支付、库存、审核等状态以真实状态机为准；含义不明时保留原文并标记待确认。
6. **只写有任务价值的内容**：文案必须帮助用户识别状态、作出决定、正确操作、理解影响或从失败中恢复；不能满足其中任一目的的说明不进入默认界面。

## 2. 核心术语表

| 场景 | 统一用词 | 使用边界 |
| --- | --- | --- |
| 新建一级业务记录 | 新建 | 新建商品、新建分类、新建订单 |
| 向现有记录加入子项 | 添加 | 添加商品明细、添加图片、添加标签 |
| 系统结果或事件 | 创建 | “订单已创建”；不作为同层级页面主按钮的混用词 |
| 进入完整编辑界面 | 编辑 | 编辑商品、编辑分类 |
| 改变单个字段或局部值 | 修改 | 修改金额、修改地址、修改备注 |
| 永久且不可恢复 | 删除 | 必须说明不可恢复，并使用危险按钮 |
| 可恢复的软删除 | 移入回收站 | 状态写“已移入回收站”；恢复动作写“恢复” |
| 从回收站不可逆清除 | 永久删除 | 必须明确不可恢复，并与“移入回收站”分开 |
| 解除关联但保留对象 | 移除 | 移除标签、移除成员 |
| 可逆关闭 | 停用 / 启用 | 状态对应“已停用 / 已启用” |
| 提交公开内容 | 发布 | 若为商品经营状态，仍以业务定义的“上架 / 下架”为准 |
| 查询 | 搜索 | 有关键词输入时使用 |
| 缩小数据范围 | 筛选 | 状态、分类、日期等条件 |
| 清空查询条件 | 重置 | 恢复默认筛选条件，不表示清空业务数据 |
| 提交表单 | 保存 | 页面/弹窗统一；明确流程终点可用“确认发货”等业务动作 |
| 放弃本次操作 | 取消 | 不写“关闭”，除非只关闭只读面板 |
| 回到上一层 | 返回 | 推荐带对象，如“返回商品列表” |
| 可设计并发布的模板本体 | 母模板 | 不用“固定模板 / 动态模板 / 新版模板”区分产品格式 |
| 仅用于显式验证的 `hero` 首屏结构 | 首屏测试样例 | 不称为“起步模板”或“内置模板库”，不暗示会自动写入新模板或页面 |
| 页面中对母模板的一次使用 | 模板实例 | 页面内容和覆盖属于当前实例，不称为“修改模板” |
| 模板画布中的中性只读内容 | 系统示例 | 不称为“默认内容”“正式内容”或“商品数据” |

## 3. 状态与视觉语义

状态标签优先使用“已…”或“待…”结构，避免把动作词直接当状态。颜色只表达语义，不单独承担信息：

| 语义 | 视觉语义 | 示例 |
| --- | --- | --- |
| 默认、草稿、未开始、不可用 | 中性 | 草稿、已停用 |
| 进行中、中性信息 | 信息 | 处理中、已发货 |
| 成功、完成、启用 | 成功 | 已完成、已启用 |
| 待处理、需要关注 | 警告 | 待审核、库存预警 |
| 失败、异常、危险终态 | 危险 | 审核未通过、物流异常 |

业务状态不能仅为统一颜色而改义。同一业务域的列表、详情、筛选项应共用同一映射；跨业务域只统一视觉语义，不强行共用状态枚举。状态必须同时显示文字或可理解图标，颜色和对比度规则引用 `docs/UI_GUIDE.md` 附录 A。

## 4. 标点、数字、单位与英文

- 中文句子使用全角标点：`，。；：？！`；括号使用 `（）`。
- 进行中提示统一使用中文省略号 `…`，不使用三个英文句点 `...`。
- 中文与英文缩写之间留一个半角空格：`商品 ID`、`SKU 管理`、`SEO 设置`。
- 数字与中文量词之间留一个半角空格：`近 30 日`、`20 件商品`；百分号和货币符号紧贴数字：`10%`、`¥1,280.00`。
- 单位首次出现时写完整，例如“金价（元/克）”；表格列内可在表头标注单位，单元格不重复。
- 缺失值统一显示长破折号 `—`；不要混用 `--`、空字符串和“无”。

## 5. 搜索、筛选与列表

- 输入框占位应说明可搜索对象，例如“搜索商品名称或货号”，避免只写“关键词”。
- 有关键词输入时主动作使用“搜索”；状态/分类/日期条件属于“筛选”。
- “重置”恢复默认条件并回到第一页；不得触发数据删除。
- 表格操作列使用具体动作，如“查看详情”“编辑”“停用”，避免只写“处理”。
- 总数使用“共 N 件商品 / 共 N 条记录”；空结果区分“暂无商品”和“没有符合当前筛选条件的商品”。

## 6. 加载、空态、错误与成功

跨页面通用词源位于 `client/src/constants/adminCopy.ts`，共享状态组件位于 `client/src/components/common/AdminDataStates.tsx`。

| 状态 | 标准结构 | 示例 |
| --- | --- | --- |
| Loading | 正在加载 + 对象 + `…` | 正在加载订单… |
| First empty | 暂无 + 对象 | 暂无订单 |
| Filter empty | 没有符合当前筛选条件的 + 对象 | 没有符合当前筛选条件的商品 |
| Permission empty | 权限事实 + 下一步 | 你没有查看订单的权限。如需处理，请联系管理员。 |
| Unconfigured empty | 尚未配置 + 对象 + 下一步 | 尚未配置物流模板。请先完成配置。 |
| Error | 发生了什么 + 下一步 | 商品加载失败。请稍后重试。 |
| Success | 对象 + 已 + 动作结果 | 分类已更新、商品已移入回收站 |

Loading 必须包含对象，不得只写“加载中…”或“正在加载…”。Error 必须区分“加载失败”和“提交失败”：加载失败优先提供“重新加载”，提交失败保留用户已填写内容并指出可检查项。

错误提示不得只写“操作失败”。能安全给出下一步时，应写“保存失败，请检查必填项后重试”或“加载失败，请稍后重试”。不得猜测网络、权限或业务原因，也不得直接显示服务端异常、堆栈、数据库字段或内部路径。安全翻译层只根据已审核的错误码/状态码生成用户文案；未知错误使用本地兜底，并把内部详情留在受控日志中。

共享安全映射至少覆盖：登录状态失效 → “请重新登录后继续”；权限不足 → “如需处理，请联系管理员”；并发冲突 → “数据已被其他操作更新，请重新加载后再试”。这三类提示不得暗示系统已自动恢复。

## 7. 确认文案

确认弹窗按“动作对象 + 直接后果 + 是否可恢复 + 下一步”组织：

| 场景 | 标题 | 正文 | 主按钮 |
| --- | --- | --- | --- |
| 删除 | 删除“对象名”？ | 删除后不可恢复。请确认是否继续。 | 确认删除 |
| 停用 | 停用“对象名”？ | 停用后将不再显示/不可继续使用，可稍后重新启用。 | 确认停用 |
| 发布 | 发布“对象名”？ | 发布后将对目标受众可见。请确认内容已完成核对。 | 确认发布 |
| 审核通过 | 通过“对象名”的审核？ | 通过后将进入下一业务状态。 | 确认通过 |
| 审核未通过 | 不通过“对象名”的审核？ | 请填写原因，提交后相关人员可查看。 | 确认不通过 |

“删除”“永久删除”“停用”“移入回收站”不得互相替换。危险确认按钮必须复述动作，不使用含糊的“确定”“确认”或“继续”。共享 `AdminConfirm` 只允许非危险操作使用默认“继续”；危险调用必须显式提供标题、后果和动作按钮文案。

## 8. 表单、批量与冲突反馈

- 表单标签使用名词，帮助文字解释填写规则，占位文字只提供示例或输入范围；不要用占位文字代替标签。
- 校验错误紧邻字段并说明修正方法，例如“请输入商品名称”或“售价必须大于 0”；不写“格式错误”。
- 离开未保存表单时写“放弃未保存的修改？”，正文说明未保存内容会丢失，按钮写“放弃修改”。
- 批量操作必须写出对象和数量，例如“停用选中的 8 件商品”；执行前后均保留数量，避免只写“批量处理”。
- 部分成功采用“已完成 N 项，共 M 项；未完成项请检查后重试”，并提供失败项列表或导出入口；不得把部分成功显示为全量成功。
- 并发冲突不覆盖他人修改。提示“数据已被其他操作更新，请重新加载后再试”，必要时提供“复制当前填写内容”，但不自动提交旧版本。
- 会话失效先说明当前操作未完成，再引导重新登录；权限不足说明当前不可执行及联系对象，不伪装成“数据不存在”。
- 模板设计的对象、生命周期与操作影响遵守[唯一标准](page-builder/template-creation-rules.md)，具体页面交接按[从属编辑细则](page-builder/template-design-framework.md)展开。“恢复历史版本为草稿”与“回滚线上版本”、“保存模板”与“发布模板新版本”、“移入回收站”与“永久删除”不得混用。模式和对象持续可见时，工具栏可用“保存草稿”“发布”等短标签；确认标题、危险按钮、无障碍名称、成功/失败反馈必须写清页面或模板对象及真实影响。

## 9. 说明、帮助与 AI 辅助内容

后台说明采用“必要结论 → 当前影响 → 下一步”的顺序。默认界面不写欢迎语、自我介绍、重复标题、操作前寒暄、显而易见的字段释义、对刚完成动作的完整复述或没有当前行动价值的泛化建议。必要的风险、限制、数据影响和恢复方法不因追求简短而省略。

- 字段帮助只解释标签本身无法表达的填写规则、来源、边界或后果；同一事实不得同时出现在标题、标签、占位文字、帮助文字和提示框中。
- 页面级说明只保留影响当前任务的前置条件和限制。背景知识、示例、历史记录和低频说明可以按需查看，但不得抢占主要任务层级；其显示与折叠行为按 `docs/UI_GUIDE.md` 附录 A.5 执行。
- 成功反馈只确认真实完成的对象和结果，不复述全部输入，不追加未经请求的建议；部分成功、未保存、排队中或仅生成草稿不得写成“已完成”。
- 空态只说明当前事实和一个最相关的下一步；无可执行动作时不为了填充版面编造 CTA。

后台内置的 AI 建议、摘要、解释和生成结果还必须满足以下要求：

1. 默认先给可核对的结论或产物，再给必要依据、限制和下一步；不展示模型的自我评价、过程复述、重复总结或与当前任务无关的延伸建议。
2. AI 建议与系统事实、已保存数据和实际执行结果必须在视觉和措辞上明确区分；使用“建议”“草稿”“待确认”等真实状态，不得用“已保存”“已发布”“已处理”暗示尚未发生的操作。
3. AI 不得自动增加用户未要求的字段、步骤、业务承诺或高风险操作。扩展解释和备选方案按需提供，并保留用户明确查看详情或继续生成的入口。
4. 涉及权限、价格、库存、订单、支付、发布、客户数据或其他高风险事实时，必须引用当前系统可核对的信息或明确标记未知；不能用流畅文案补齐缺失事实。
5. 用户编辑、拒绝或关闭 AI 内容后，不得自动恢复、覆盖或再次插入；生成失败时保留用户原有内容，并说明失败事实和可执行的重试方式。
6. AI 或批量修改优先用字段/节点级“原值 → 建议值”展示可应用、跳过、冲突和排除项，并提供接受、拒绝、聚焦变化和撤销；不使用一段总结代替可核对差异。
7. 生成结果必须持续标识目标对象、基线版本和“未保存”状态。接受建议只表示写入当前编辑会话，不得用“完成”“已应用到线上”暗示保存、发布、回滚或批量更新已经发生。
8. 当对象或基线已经变化时，提示“建议基于旧版本，尚未应用”，并提供重新比较或保留当前内容的动作；不写成普通网络失败，也不自动把旧建议套到新对象。

文案评审使用一个删除测试：删除某句后，如果不影响用户判断状态、完成任务、理解风险或恢复错误，就删除该句；如果会影响其中任一项，就保留并放在用户需要它的位置，而不是统一藏入“更多说明”。

## 10. 治理、落地边界与待确认项

- 通用按钮、异步反馈、空态和确认弹窗从共享词源读取。
- 静态门禁检查泛化 Loading、泛化危险确认和共享词源漂移；业务例外必须写入白名单并注明原因，不能通过改写正则绕过。
- 规范迁移按共享词源、共享状态组件、代表页面、其余业务页分批完成；禁止仓库级机械替换。
- 订单、支付、退款、库存、履约、商品上下架等状态保留在各业务域的映射中，确认状态机含义后再收敛为域内单一来源。
- “用户”在后台可能指员工或客户；新文案必须明确写“后台员工”或“客户”。既有页面名称需结合权限与数据模型逐页确认，不在纯展示文案任务中擅自改义。
- 法律承诺、经营承诺、审核依据和对外发布范围必须由业务负责人确认，不能为了语言统一而改写。
