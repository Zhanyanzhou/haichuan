# 管理后台增量开发规则

> 适用范围：管理后台的功能、接口、权限、状态、入口和运营交互。后台已具备基础管理能力；后续只做增量优化、统一标准、避免重复建设，不按从零重构处理。
> 文案只认 `docs/ADMIN_COPY_GUIDE.md`；排版、密度与无障碍只认 `docs/UI_GUIDE.md` 附录 A。本文不另建视觉或文案标准。
> 最近核对：2026-09-16。

## 决策优先级

兼容现有业务 > 复用现有能力 > 保持一致性 > 提升运营效率 > 降低维护成本 > 新功能丰富度 > 视觉创新

任何新功能如果明显破坏前四项，应重新设计。

## 开发前必须回答

1. **现有能力能否复用？** 相同业务、交互、组件、状态、权限或数据服务已存在时，必须复用或扩展。
2. **这次修改会不会破坏现有行为？** 不得隐式改变旧数据、旧状态、旧权限、旧接口或旧页面语义。
3. **这项能力以后是否应该成为公共能力？** 现有搜索、筛选、分页、上传、权限、状态展示、反馈、弹窗、校验、日志、导入导出不足时，优先升级公共能力，禁止页面内特例。

三个问题没有答案前，不进入实现。

## 1. 复用，不平行建设

新增功能前先判断现有后台是否已有相同业务能力、交互模式、组件、状态处理、权限或数据服务。已有能力能够满足需求时，必须复用或扩展，禁止第二套实现。

本质上属于已有能力延伸的，在原能力上扩展。只有业务语义、生命周期或权限模型明显不同，才允许独立模块。禁止把“多一个字段、多一个状态、多一个入口”升级成新系统。

同一业务对象保持一个主要管理入口。其他模块优先跳转、关联、快捷操作或只读展示，禁止多个互相独立的维护入口。模板组件库预览图复用现有素材选择器与页面素材库，上传后在同一对话框内按当前模板画幅裁切，并以图片槽位线框对照构图，再登记为新的页面素材；作为模板身份上的可选目录辨认图，不另建封面上传器，也不进入模板定义或客户前台。卡片按该模板画幅完整显示已确认构图，不再用固定 4:3 或 CSS 自动裁切。

## 2. 局部需求服从整体规则

单个页面或模块不得随意引入新的操作方式、状态模型、表单规范、列表规范、权限模式、错误处理或数据返回结构。现有列表、编辑、保存、删除、发布、筛选、批量操作和提示反馈必须沿用；现有模式有问题时统一修正，不做局部例外。

已被运营稳定使用的交互不轻易改变。调整时优先保证：操作路径不明显增加、常用入口不消失、原有业务语义不改变、历史习惯尽量保留。

## 3. 允许优化，禁止无收益重构

仅在以下情况允许重构：明确业务错误、明确影响运营效率、明确安全或数据风险、明显阻碍后续扩展、存在重复实现或严重维护成本。不得因为“写法不够漂亮”“想换架构”“想统一风格”做大范围重构。

默认路径：小范围修改 → 验证 → 稳定 → 再扩展。禁止在没有明确收益和迁移方案时整体推翻现有后台。

开发当前功能时可修复直接相关问题；不得因发现历史问题无限扩大范围。非阻塞问题记录后单独处理。

发现后台混乱时，优先修规则、状态、权限、组件、数据模型或交互逻辑的不统一，禁止只针对页面视觉做局部修补。

## 4. 状态、配置、入口与暴露范围

已有状态能够表达业务时，不新增状态。只有业务流程出现新的独立阶段才增加状态。禁止为页面展示方便增加伪状态；展示标签不等于业务状态。

已有固定业务规则，不因单次需求随意配置化。只有同时满足“业务会变化、运营需自主调整、调整频率足够高、风险可控、含义明确”才允许配置。

新功能默认只暴露给真正需要它的角色和场景：高频直接展示，低频收纳，高级能力放到二级入口。技术能力不得进入普通运营界面。

## 5. 语义、数据与安全

新增字段、状态、配置或交互时，不得悄悄改变已有数据含义。涉及已有业务语义变化时，必须明确处理历史数据、旧状态、旧权限、旧接口和旧页面行为。

新增需求优先兼容现有数据模型。只有现有模型无法正确表达业务时才修改核心结构。禁止为前端展示方便随意新增数据库字段，禁止因短期需求破坏已有数据一致性。

后端规则保持单一来源：复用现有 Service、Domain 或公共逻辑，禁止在新页面或新接口复制同一套判断。

高风险操作必须接入既有权限、审计、状态校验、二次确认和数据校验。禁止因为“方便”绕过保护，新增功能不能成为安全规则的例外。
