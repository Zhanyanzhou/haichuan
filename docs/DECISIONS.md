## A. 已批准且有效的决策（✅）

### A.1 状态管理用 Zustand 4（非 Redux）✅
- **决策**：前端全局状态用 Zustand 4。
- **原因**：无 Provider、无 boilerplate、selector 模式避免不必要渲染、体积小（~2KB）。
- **当前事实**：`authStore`、`shopStore` 用 `persist`；`selectionStore`、`pageMetaStore`、`appStore` 非持久。

### A.2 固定技术栈 ✅
- **决策**：前端 React 18 + TypeScript 5 + Vite 8 + Ant Design 5 + Tailwind CSS 3 + Zustand 4；后端 NestJS 11 + Prisma 5 + MySQL 8 + JWT + bcrypt + Sharp。当前不常驻 Redis/Bull，未来恢复缓存或队列须单独决策。
- **原因**：围绕展示、商品管理、内容编辑、选款咨询定位选型。
- **约束**：不得自行替换/升级/降级；当前版本事实以依赖清单、锁文件和运行结果为准，技术不变量与禁止替代项见 `PROJECT_RULES.md` §0。

### A.3 统一响应结构 ✅
- **决策**：后端全局 `TransformInterceptor` 包成 `{code,data,message,timestamp}`；前端 `utils/unwrap.ts` 解包。
- **原因**：前后端契约统一，避免各页面重复解包逻辑。

### A.4 两套独立认证体系（User / Customer）✅
- **决策**：后台 `User` 与前台 `Customer` 是两套独立认证；**共用 `JWT_SECRET`**，靠 payload `type` 字段区分。
- **原因**：区分员工后台与前台客户/游客，复用同一套 JWT 基础设施。
- **当前事实**：后台 `JwtAuthGuard` + `JwtStrategy`（payload `{sub,username,role}`）；前台 `CustomerAuthGuard` / `OptionalCustomerAuthGuard`（payload `{sub,type:"customer"}`，过期 24h 写死）。
- **注意**：是否拆分双 secret 见 🟡 D.6。

### A.5 RBAC 用角色白名单（@Roles + RolesGuard）✅
- **决策**：后端权限只做**粗粒度角色白名单**（`@Roles(...)` + `RolesGuard`），不做细粒度权限守卫。
- **原因**：角色少、场景明确，避免过度设计。
- **影响**：前端 `permissionStore` 的细粒度权限键后端**不校验**；前端隐藏 ≠ 服务端拒绝（见 `PROJECT_RULES.md` §2、🟡 D.4）。

### A.6 装修采用 Puck PageDocument ✅
- **决策**：前台页面装修统一用 Puck `PageDocument` 体系（草稿/发布/版本回滚 + 多设备预览）。
- **原因**：所见即所得、内容与业务分离、支持模板与发布流。
- **当前事实**：`PageDocument`/`PageTemplate`/`PageDocumentRevision` + `page-modules` 后端 + `pageDocumentApi` + `HomepageConfig` 编辑器 + `PuckDocumentRenderer` + `components/blocks` + `page-builder/adapters`。
- **注意**：旧首页内容块与 `ContentSlot` 已归档；当前边界见 ✅ D.8，历史错误结论见 B 节索引。

### A.7 新增样式优先 Tailwind ✅
- **决策**：新代码优先 Tailwind 类名，仅动态计算值用行内样式；不强制重写已有代码。
- **原因**：历史组件 Tailwind / 行内样式混杂，统一未来方向即可（见 🟡 C.1）。

### A.8 客户前台采用高级珠宝品牌级数字体验体系 ✅
- **决策日期**：2026-08-17；项目负责人明确要求以“顶级奢侈品珠宝品牌网站”为目标，形成高级、简约、奢华但克制的统一规则。

### D.2 ✅ 当前阶段交易与真实资金保持关闭（2026-08-23）

- **真实资金门禁**：在真实资金能力另行获批、目标环境与商户配置核验，并完成成功、失败、回调、退款、对账和回退验收前，客户与后台均不得发起外部支付网关收款；后台可保留历史查看、非网关人工审核和售后。服务端必须以单一、显式且安全默认关闭的门禁阻止所有新网关交易，同时继续安全处理暂停前已创建交易的有效回调；具体接线和验证状态只认代码与 `docs/CURRENT_STATE.md`。
- **后续解冻**：支付和生产上线最后单独讨论；必须逐能力记录环境、身份、真实数据、凭据、资金路径、审计、回退和上线批准，不得整体一次性解冻。

### D.3 ✅ Feature Flags 已服务端单一来源化（2026-08-15 复核修订）
- **已落地**：服务端 `GET /settings/flags` 读取 `CUSTOMER_COMMERCE_ENABLED` 环境变量作为**单一来源**；前端 `featureFlags.ts` 拉取该端点，请求失败回退 `SAFE_FLAGS`（三项全 false，安全默认关）。服务端 `CustomerCommerceGuard` 仍是最终安全边界。
- **2026-08-20 校正：** `docker-compose.yml` 与 `.env.example` 均以 `false` 为默认值；获批环境必须显式设置为 `true`，不得依赖缺失变量时的默认开放。
- **历史状态（已过时）**：曾为前端硬编码 false。

### D.4 🟡 权限粒度
- **现状**：后端只做 `@Roles` 角色白名单（粗粒度）；前端 `permissionStore` 有细粒度权限键但后端不校验。
- **待定**：是否引入后端细粒度权限守卫；前端隐藏与后端拒绝的边界如何统一。

### D.5 🟡 Category 删除语义
- **现状**：`Category.deletedAt` 是死字段；删除实际只写 `isActive:false`，读查询按 `isActive` 过滤。
- **待定**：分类采用软删除（启用 `deletedAt`）还是停用（`isActive`）；是否清理 `deletedAt` 字段。

### D.6 🟡 JWT 双域 secret / 全局 Guard
- **现状**：admin 与 customer 共用 `JWT_SECRET` 靠 `type` 区分；`JwtAuthGuard`、`RolesGuard`、`ThrottlerGuard` 已注册为全局 Guard，接口默认要求后台身份，匿名或客户域接口通过 `@Public()` 后叠加相应客户守卫。
- **待定**：是否拆分双 secret / 双 strategy；是否为客户会话增加独立吊销、刷新与风险控制机制。

### D.7 ✅ checkout 客户认证与交易关闭语义（2026-08-20）
- **决定**：`POST /customers/checkout`、付款凭证提交与付款凭证上传均先经 `CustomerAuthGuard`；无客户令牌或无效令牌统一返回 401。认证成功后才由 `CustomerCommerceGuard` 判断交易开关，关闭时返回 503。
- **理由**：认证是交易写入的首要边界；交易关闭不能替代身份校验，也不得让游客借由开关状态绕过未登录语义。
- **边界**：这只收敛接口的认证与关闭行为，不代表交易、支付或生产上线获批；实际开放仍遵循 D.2 的环境、经营和真实联调门禁。

- **待定**：是否启用多仓、默认仓库设定、存量库存归属、跨仓调拨与前台可售口径。

### D.18 ✅ 商品、库存、发布与员工权限经营规则（2026-08-23）

- **销售模式**：保留 Schema 当前定义的 `DISPLAY_ONLY`、`SELECTION`、`APPOINTMENT`、`DIRECT_PURCHASE`、`CUSTOM_INQUIRY` 五种 `SalesMode`；它决定作品的公开主行动与对应发布门禁，不能降级为展示标签，但不等于排他的报价通道。报价通道与客户资格由 D.19 决定。
- **价格事实**：`DIRECT_PURCHASE` 的成交价只认有效 `ProductSKU.price`；`Product.price` 是有效 SKU 最低价的派生缓存，不接受运营、导入或旧编辑器直接建立第二个价格事实源。
- **库存事实**：`Inventory` 是可售、预占、核销与释放的唯一库存来源；`ProductSKU.stock` 只作遗留兼容或非权威展示。`InventoryPolicy` 保留 `STANDARD / SINGLE_UNIT`，单件策略在 SKU、库存、购物车与订单数量上统一执行。
- **发布与售罄**：按 `SalesMode` 执行公开行动与发布门禁；当前零售购物车、零售结算和直接下单只允许 `DIRECT_PURCHASE`。其 0 库存不阻止发布，但必须显示真实不可购买/售罄状态并拒绝上述零售路径；这不排除未来高级定制或合作蜡模在客户确认报价后按独立状态机形成订单。不得用假库存或倒计时制造稀缺。
- **员工权限**：`WAREHOUSE` 不进入付款查看或审核；`CUSTOMER_SERVICE` 保留售后权限；员工删除改为仅 `SUPER_ADMIN` 可执行的禁用，不做物理删除。后续任何角色范围变化仍按高风险权限变更审批。
- **迁移边界**：`InventoryPolicy` migration 文件存在不代表已经执行。未确认精确数据库目标、迁移状态、备份与回退并获得针对性批准前，不执行 migration 或真实数据回填。

### D.19 ✅ 双客群、三报价与合作蜡模经营框架（2026-08-23）

- **专项决定职责**：本条是双客群、三报价、客户确认、合作蜡模价格、资源门禁和订单冻结的业务执行决定源。项目定位、品牌原则、公开页面职责和长期产品边界以 `docs/PROJECT_GUARDRAILS.md` 为准，本条不得改变这些方向。在方向不冲突的前提下，报价、定价、状态机、事务转单和订单快照等业务细节发生冲突时以本条裁决，实施时再核对当前 Schema、代码与运行事实。`PROJECT_RULES.md` 固化硬门禁，`docs/PRODUCT_DATA_CONTRACT.md` 定义数据字段与必要校验数值，`docs/DATA_AND_API.md`、`docs/MODULES.md` 只作派生导航与目标边界。
- **方向承接**：公开网站定位、客户旅程和合作入口只认 `docs/PROJECT_GUARDRAILS.md`；本条只在该方向内定义普通客户、高级定制与审核通过合作商的报价和订单执行细节。
- **`SalesMode` 与报价通道**：`SalesMode` 是作品对外呈现的公开主行动模式，分别表达展示咨询、选款、预约、标准直购或定制报价；它不等于排他的报价通道，也不承载客户身份、合作资格或专属价。同一作品/设计不因客群复制商品，可以独立存在标准零售固定价、高级定制报价和合作蜡模报价三个通道；客户资格与价格协议由各通道独立裁决。
- **当前零售边界**：当前零售购物车、零售结算和直接下单只接受 `DIRECT_PURCHASE`。这只是现有零售路径的门禁，不表示未来只有 `DIRECT_PURCHASE` 才能形成订单；高级定制和合作蜡模在客户本人确认有效报价后，可以按各自状态机转为订单。
- **报价流程与本人确认**：高级定制执行“客户提交需求 → 后台创建/修订报价 → 已认证客户本人确认 → 事务转单”；合作蜡模按确认文件版本、蜡种、确认蜡重和有效合作克价形成版本化报价，再由已认证合作客户本人确认。后台员工可以创建或修订报价，但不得代替客户完成确认；报价修改后必须产生新版本并重新确认。
- **蜡模事实**：红蜡、紫蜡是依据 3D 文件打印的 1:1 模型；文件根据客户要求的目标重量制作并具有固定蜡重。结算只认确认的文件版本和蜡重；“预计金重约为蜡重十倍”只作内部生产参考。
- **合作价格**：币种为 CNY，系统默认紫蜡 20 元/蜡克、红蜡 25 元/蜡克。合作商可拥有明确的客户专属双克价；有效专属价优先，否则回退系统默认价。`SUPER_ADMIN` 与 `ADMIN` 可以维护价格，但必须记录前后值、生效/失效、原因、操作者与时间。
- **分通道资源门禁**：标准零售按 SKU 与 `Inventory` 裁决；高级定制按确认报价、产能、材料和适用工艺裁决；合作蜡模按确认报价、3D 文件版本、蜡模产能和材料裁决。不得用成品零售 Inventory 代替定制或合作门禁，也不得绕过零售库存。
- **事务转单与完整快照**：报价确认与转单必须在服务端事务内完成身份、报价版本、资格、资源门禁和金额复核，并以幂等键防止重复订单；失败不得留下“已确认但无订单”、部分订单或重复订单。所有订单都冻结客群、报价通道、确认主体与时间、币种、费用明细和总额；零售订单另冻结所选 SKU、数量与成交单价，定制订单另冻结需求及报价版本，合作订单另冻结蜡种、3D 文件版本、目标金重、确认蜡重、采用克价及来源。任何后续调价、配置或资料变化不得改写历史报价或订单。
- **附加费用**：可按固定金额、按克或按订单配置适用客群、启停和客户可理解说明，并在确认前逐项展示；具体费用项目和金额由后续实际经营配置。
- **合作申请与客户管理**：申请资料包括公司/商户名称、联系人、手机、地区、主营业务、预计月用量、营业执照或资质、合作说明，并由后台人工审核。只有已通过客户可读取合作价格和创建合作订单；暂停后禁止新合作价格与新订单，历史记录继续保留。后台客户管理覆盖审核、专属双克价、生效区间、调价历史、普通/定制/合作订单与审计。
- **资金门禁**：支付继续关闭；任何客户或后台外部网关收款都必须消费服务端全局资金门禁，不能只靠页面隐藏、路由限制或客户交易开关。
- **已知实现缺口**：当前 Schema、API、后台和订单流程尚未完整实现三报价、客户本人确认、分通道库存/产能/材料门禁、事务转单和完整不可变快照；完整能力具备前，员工确认与报价转单必须保持安全暂停。本决议只批准产品目标，不表示上述缺口已修复；任何数据库、权限、订单金额或支付实现仍按 `AGENTS.md` 单独审批和验收。

### D.20 ✅ 成熟网站共享底座与最终交付形态（2026-08-24）

- **语言与市场**：以中国大陆为主要服务区域，完整支持中文与英文；中文采用无前缀规范路径，英文采用 `/en`。本决定要求两种语言覆盖同一核心旅程、法律信息和交易条件，不把自动回退或机器翻译视为已发布内容。
- **经营目标**：标准零售、高级定制和合作蜡模都以真实交易为长期目标，继续服从 D.18/D.19 的单一作品、`ProductSKU.price`、`Inventory`、版本化报价、客户本人确认与不可变快照边界。微信支付与支付宝是目标渠道，但当前资金门禁继续关闭，不能因 Schema、SDK 或页面存在而启用。
- **内容职责分离**：`EDITOR` 仅可保存草稿、预览并提交审核；`ADMIN` 与 `SUPER_ADMIN` 才可复核和发布。每个语言版本独立记录审核状态、发布版本指针与内容哈希，发布不得覆盖历史版本。
- **会话与请求安全**：后台员工与前台客户维持两套独立刷新会话；浏览器目标态使用 `HttpOnly` Cookie，Cookie 鉴权的写请求必须同时通过 CSRF 与精确 Origin 校验。现有 Bearer 调用在迁移期兼容保留，不因此削弱服务端权限或交易门禁。
- **隐私、通知与集成**：分析写入必须等待明确同意；服务同意、营销同意与分析同意分别留痕。通知以站内信为事实主体，短信与邮件作为可审计投递；物流经快递100适配层接入。P0 只建立合同和安全默认关闭的基础，不启动第三方发送。
- **可靠通知不变量**：服务通知与营销通知分离；涉及订单的通知以订单快照作为收件事实源，外部投递安全默认关闭。账户注销事务已经取消的投递不得被 Worker 重新激活、改写为成功或重新排队。具体已接入事件、运行开关和验证范围属于易变实现事实，必须按当前代码与 `docs/CURRENT_STATE.md` 重新核验。
- **前端与部署**：前端采用 Vite 混合预渲染，公开稳定路由可生成可索引快照，认证、个性化和编辑页面继续客户端运行；快照必须与已发布内容哈希对应。最终生产门禁以 Docker 单机部署为目标形态，部署、迁移、回滚、备份恢复和目标环境验收仍需单独批准。
- **P0 数据合同**：采用加法式本地化、媒体资产与变体、独立刷新会话、同意记录、通知与投递偏好、数据库 Outbox、内容审核与发布指针、价格申请历史、版本化报价与付款计划、合作价格协议与 3D 文件版本、物流事件和 SEO 快照。它们扩展既有事实源，不建立第二套商品价格、库存或页面内容来源。
- **回退与重审**：P0 migration 只作为手写静态合同交付，不在本决定中授权执行；任何真实数据回填、交易开放、外部投递、支付、部署或生产写入仍按 `AGENTS.md` 和目标环境门禁单独处理。

### D.22 ✅ 模板商业目的进入机器合同（2026-08-25）

### D.23 ✅ 标准零售在线支付与原路退款主链（2026-08-25）

- **正式主链**：标准零售由认证客户本人在自己的订单上下文中发起在线支付，服务端只按订单剩余应收创建渠道交易，并以验签回调或主动查单确认到账。后台生成收款码是辅助能力；银行转账与门店收款只用于已约定的特殊订单或渠道异常，不是普通客户结算默认项。
- **首发范围**：首发覆盖桌面网站与手机网站，微信支付优先，支付宝第二批，暂不包含小程序。桌面端使用 Native 二维码，普通手机浏览器使用 H5；微信内网页只有在认证公众号、商户号与公众号 AppID 绑定、该 AppID 下的用户 `openid`、支付目录和真实联调全部具备后才开放 JSAPI，不能把开放平台网站扫码登录的 `openid` 直接复用为公众号支付身份。
- **结果裁决**：前端跳转、支付控件回调或管理员填写均不能证明到账。支付成功、取消、失败和超时恢复必须通过服务端回调/查单裁决；待支付交易重试复用原商户单号，关单前先查单，结果不确定时不得生成第二个可支付单号。
- **退款方向**：在线付款审核通过后原路退回，并以渠道受理、查询或回调事实推进；人工不得把微信或支付宝退款直接标记成功。线下异常退款可以人工执行，但必须具备流水、操作者和审计时间线。
- **上线边界**：代码、SDK、Mock 和构建均不等于真实资金可用。商户资质、凭据、正式域名、回调、查单、关单、退款、对账和隔离目标环境真实验收完成并再次批准前，`CUSTOMER_COMMERCE_ENABLED` 与 `PAYMENT_GATEWAY_TRANSACTIONS_ENABLED` 继续安全默认关闭。

### D.24 ✅ Migration 历史签认与不可变发布制品（2026-08-27）

- **遗留事实与唯一例外**：`20260824115000_add_product_publication_quality` 在首次纳入 Git 前已应用，备份 ledger 的 SHA-256 与当前仓库文件不同，原始字节无法从 Git、现存镜像或本地对象恢复。不得改写 migration 文件或 `_prisma_migrations`。只在 migration 名称、当前仓库 SHA-256、ledger SHA-256，以及 `products` 三列和 `products_publication_quality_idx` 的结构合同全部精确匹配时，接受 `server/prisma/migration-integrity-exceptions.json` 中这一项签认；任一值偏离即阻断。
- **后续历史不可变**：所有新 migration 只能追加。CI 比较基准与目标 commit，禁止对既有 `migration.sql` 修改、删除或重命名；静态校验同时核对例外清单引用的当前文件哈希。例外清单不是跳过 Prisma 校验的通用机制，增加或修改例外必须重新形成可审计决定。
- **发布前数据库门禁**：`release-preflight` 把仓库 migration、目标库 `_prisma_migrations`、未完成/重复/缺失记录、未知 checksum 漂移和已签认结构共同验证。只有精确匹配的一个遗留例外可被计为接受；待执行 migration、未知漂移或结构不符均保持阻断。
- **不可变制品**：server/client Docker 基础镜像及 Compose 第三方镜像固定到 digest。手动 `Release Images` 工作流从精确 commit 构建并推送 GHCR，生成 SBOM、provenance、签名证明和 `release-manifest.json`；镜像 OCI 标签记录源码 revision、来源、组件和 migration bundle SHA-256。生产只接受清单内 `image@sha256:...`，必须先拉取并验证摘要与标签，启动使用 `--no-build`，禁止在生产主机源码构建或依赖浮动 tag。
- **维护与权限边界**：基础镜像 digest 更新属于显式供应链维护，必须核对上游版本、安全公告并重新构建验证。该决定与本次实现不授权修改当前数据库、执行生产 migration、写入真实 `.env`、Git 提交/推送、注册表推送或生产部署；首次真实制品仍需单独批准并手动触发。
- **联系页面顺序**：联系页面正式发布门禁排在 migration 历史完整性和首个可验证不可变制品之后。在这两项形成当前目标环境证据前，不以页面存在、草稿或本地构建宣称联系流程已完成。

### D.25 ✅ 员工与会员统一密码长度合同（2026-08-28）

- **当前冲突（待裁决）**：本决定仍是已批准产品决定，但截至 2026-09-08，客户端实际为会员 `8–64`、员工 `12–64`，服务端策略亦为会员 `8–64`、员工 `12–64`，且员工密码会拒绝常见弱口令。文档整理不擅自选择决定或代码覆盖另一方；在项目负责人批准保留 D.25 或形成明确替代决定前，不得把两者描述为已对齐。
- **业务决定**：项目负责人明确接受安全取舍；后台员工、首管理员、Demo 管理员与前台会员在新建或重置密码时统一为 `6-18` 位，只校验长度，不追加大小写字母、数字、符号或常见密码限制。
- **单一事实源**：服务端账号级常量与断言定义在现有员工密码策略模块中，员工、会员、微信新账号与 CLI 共用；客户端由统一配置供后台员工表单、会员注册和重置页面消费，目标测试保证两端数值一致。
- **历史兼容**：本决定不重置、不迁移也无法从哈希反推既有密码长度。登录、注销确认和微信绑定既有手机号继续按原密码哈希校验，并保留最多 128 位的历史凭据输入边界；只有创建新密码或重置密码强制 `6-18` 位，避免现有账号因规则收窄被直接锁死。
- **不变安全措施**：密码继续只保存 bcrypt 哈希，当前哈希轮次、登录错误锁定、会话撤销、短信验真、角色权限、审计脱敏和生产 Demo Seed 禁用门禁不变。密码不得进入日志、文档、截图或响应。
- **回退与重审**：若出现撞库、弱口令滥用或合规要求变化，应重新审议复杂度、泄露密码阻断、多因素认证或强制轮换；任何真实账号批量重置、生产配置或部署仍需单独批准。
