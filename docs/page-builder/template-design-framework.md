# 页面装修与模板设计统一规则

> 本文件是页面装修与模板设计的专项产品架构入口，只规定模板模型、双模式职责、数据边界、生命周期、兼容策略和变更原则。
> 产品与品牌方向只认 `docs/PROJECT_GUARDRAILS.md`；视觉、交互、响应式和无障碍只认 `docs/UI_GUIDE.md`；执行与验证只认 `WORKFLOW.md`。
> 当前模板数量、实现、迁移和验证状态只记入 `docs/CURRENT_STATE.md`，不得反向定义本文件的长期边界。
> 最近核对：2026-09-03（确立模板设计框架优先，内置模板降为兼容与起步样例）。

---

## 1. 产品模型

店铺装修的核心产品是可持续扩展的模板设计框架，而不是预先维护固定数量的成品模板。新能力应优先完善节点、槽位、构图、样式、响应式、页面可编辑范围、版本和渲染链路；不能把补齐某一批模板的具体文案、图片或视觉成品当成框架完成。

产品只向运营者提供一套母模板模型：所有可新建、设计、保存、发布并加入页面的模板都使用版本化 `TemplateDefinitionV2`。分类、来源、用途和状态只是模板元数据，不得形成“固定模板”“动态模板”“新版模板”等并列业务模型。

现有内置模板继续承担两项职责：

- 为历史页面和旧数据提供兼容重放；
- 为新设计提供可选择的起步结构。

它们的当前数量、具体内容和完成度是实现事实，不是产品边界、固定路线图或所有模板任务的永久验收目标。新增母模板不以加入内置模板清单为前提。

母模板是完整根构图，不把内部媒体、文字、行动或业务对象降级为页面根画布散件。自由设计仍受注册节点类型、嵌套、尺寸、令牌、品牌和发布合同约束，不接受任意 HTML/CSS 或可执行组件上传。

## 2. 事实来源

| 来源 | 唯一职责 |
| --- | --- |
| `contracts/page-builder/template-definition.schema.json` | 母模板、节点、槽位、响应式规则和页面实例覆盖的结构与能力边界 |
| `DynamicTemplate` 草稿及不可变版本 | 实际模板身份、可编辑定义、目录状态、发布版本和校验摘要 |
| `contracts/page-builder/content-templates.contract.json` | 当前内置起步/兼容模板的登记与布局合同，以及现有页面级规则 |
| Puck `PageDocument` | 页面中的模板实例、真实内容和合同允许的实例覆盖 |
| 本文件 | 人需要理解的产品模型、双模式分工、生命周期和兼容原则 |

Renderer、Inspector、模板目录、适配器、生成类型和校验器都是上述来源的消费者，不得维护可独立漂移的模板清单、比例表、槽位表、预览构图或页面门禁。

`content-templates.contract.json` 不是所有未来母模板的目录；`template-definition.schema.json` 也不是实际模板记录库。需要判断“允许怎样设计”时查结构合同，需要判断“有哪些模板和版本”时查 Repository，需要判断“页面实际显示什么”时查 `PageDocument` 与其锁定的模板版本。

## 3. 一套编辑器，两种模式

页面装修与模板设计建立在同一 Shared Editor Core 上，共享 Template Repository、Renderer、Canvas 基础设施、结构树与属性控件基础能力、视口、预览和 History 基础设施。两种模式可以使用隔离的 Store 和会话状态，但不得因此复制可独立漂移的编辑器、Renderer 或模板目录。

| 维度 | 页面装修 | 模板设计 |
| --- | --- | --- |
| 用户目标 | 用模板组合页面并填写真实内容 | 创建或修改可复用母模板框架 |
| 主要对象 | 当前 `PageDocument` 中的 Template Instance | Template Definition 及其完整 Node Tree |
| 可编辑范围 | 真实文字、媒体、链接、业务引用、显隐和允许的实例覆盖 | 结构、槽位语义、布局、样式、响应式和页面可编辑范围 |
| 内容表现 | 使用当前页面的真实内容 | 使用系统生成的中性只读示例 |
| 保存目标 | 当前页面草稿 | 当前模板草稿或新的模板身份 |
| 发布结果 | 发布当前页面版本 | 创建新的不可变模板版本，不修改页面 |

页面模式以 Template Instance 为结构和选择主粒度。命中模板内部可编辑内容时，可以定位到相应实例字段，但不能把内部对象升级为页面根节点或开放模板构图能力。模板模式可以按合同操作完整节点树，但不得编辑真实页面内容或业务引用。

页面和模板会话的 selection、history、dirty、preview 和 save state 必须隔离。切换模式不得自动保存、放弃、发布或合并两个会话；保存失败、并发冲突或用户取消时，必须保留对应未保存修改。

模板 Repository 的写能力只向获得模板管理权限的后台角色开放；前端 capability、快捷键、拖拽和直接 API 请求必须与服务端权限一致。当前角色与实现状态从代码和 `docs/CURRENT_STATE.md` 复核，不在本文件复制易漂移的完整动作矩阵。

## 4. 定义、示例与真实内容

模板定义、系统示例和页面实例是三个互不替代的数据层：

- **模板定义**保存结构、槽位、设计规则和页面可编辑权限，不保存真实业务内容。
- **系统示例**根据槽位类型和合同临时生成，只用于目录、模板画布和预览辨识，不持久化为模板内容。
- **页面实例**在 `PageDocument` 中保存真实内容、稳定业务引用和允许的稀疏覆盖。

系统示例必须通过与页面和公开端同源的 Renderer 呈现真实结构与比例；示例媒体保持中性，不暗示正式商品、工艺、门店、证书、价格、库存或服务承诺。示例不得上传、编辑、配置真实跳转，也不得进入新模板默认内容、页面实例、公开 Renderer 或业务引用解析。

新建母模板必须将必填的 `defaultContent` 保持为 `{}`；可选的 `previewContent` 应省略或保持为 `{}`。两者都不得写入业务内容。既有模板版本和旧个人模板中的默认/预览内容只为兼容读取，只能保持原样或由运营显式清空，不在模板设计中继续生成、修改、复制、提升或静默改写；旧页面仍按其锁定版本解释。

页面实例中的商品、分类、门店、活动、预约和服务等对象必须保存稳定引用并在运行时从各自业务事实源解析；模板和 `PageDocument` 都不得复制价格、库存、客户、订单、支付或其他经营事实。

页面覆盖默认只影响当前实例。受控反向提取仅允许有权角色显式把当前合同能无损表达的设计字段载入独立、可撤销、未保存的模板草稿；真实内容、显隐、业务引用和页面状态始终排除。该动作不得自动保存、发布、升级实例或批量修改页面，具体冲突与字段范围以当前合同和实现为准。

## 5. 生命周期与兼容

模板和页面保持两条独立生命周期：

```text
模板：本地修改 → 保存模板草稿 → 发布不可变模板版本
页面：选择精确模板版本 → 填写实例内容 → 保存页面草稿 → 发布页面版本
```

- 覆盖模板只更新同一 `templateId` 的草稿；另存为模板创建新的 `templateId`。
- 模板发布只创建该模板的下一个不可变版本，不读取、保存或发布任何页面。
- 页面实例记录精确 `templateId + templateVersion`；母模板发布后，既有页面继续使用原版本。
- 页面升级必须显式发生在页面草稿中，并在重新发布页面后才影响公开结果。
- 历史模板版本、页面 revision、兼容记录和未保存草稿不得被普通保存、打开、预览或规则收敛静默改写。

内置系统模板和旧个人模板属于兼容来源。兼容层可以读取、重放和载入统一母模板会话，但不得重新开放旧格式的创建、更新、复制或发布入口。首次覆盖兼容来源和另存为模板必须建立清晰、稳定的统一模板身份，不得覆盖原记录或当前页面。

兼容层退场必须以实际引用、可回放性、转换差异和回退证据为依据；本文件不授权删除旧记录、批量迁移模板、改写页面或执行数据库 migration。

## 6. 变更与验收

以下属于模板框架变更：新增节点或槽位能力、改变结构/嵌套/响应式规则、改变实例可编辑范围、改变模板或页面生命周期、修改共享 Renderer 或事实来源。换图、改字、选择业务对象和调整合同已允许的实例值只是页面内容编辑。

框架变更按以下顺序实施：

1. 核对当前结构合同、Repository、页面合同、Renderer、校验和存量兼容路径。
2. 说明用户结果、存量影响、兼容方式、回退和所需权限。
3. 只在对应权威来源修改事实，并让生成物与消费者同步读取；不得在调用方复制新规则。
4. 按实际影响验证模板设计、页面实例、保存/重载、版本、公开 Renderer 和失败路径。

验收以能力与受影响面为单位，不以固定模板数量为单位：

- 新增母模板应能在不修改内置模板清单的前提下完成创建、结构设计、双端构图、保存、发布和页面插入。
- 页面填写真实内容不得修改母模板；模板发布不得自动升级页面。
- 系统示例不得进入模板持久化、页面实例或公开结果。
- 修改节点、槽位或共享 Renderer 时，覆盖受影响的节点/槽位类别、视口、状态和兼容适配器；只有改动内置兼容合同或全目录行为时，才要求对应兼容模板集合的全量回归。
- 构建、Mock、合同检查、浏览器视觉、真实 API/数据库和生产证据分别证明不同层级，完成结论按 `WORKFLOW.md` 限定。

临时设计稿、逐模板设计卡、历史批次清单和审计结论不构成现行规则。确需长期保留的产品取舍写入 `docs/DECISIONS.md`；当前数量、完成度、迁移和验证证据写入 `docs/CURRENT_STATE.md`。

## 7. 冲突裁决

先区分争议是在问“现在实际怎样”，还是“以后应当怎样”，不得用实现现状否定已批准方向，也不得把目标规则冒充为已经实现。

- **当前事实**：实际运行与真实页面优先，其次是当前机器合同、Repository 数据、代码、类型、Schema 和配置，再其次是已核对的 `docs/CURRENT_STATE.md`；历史审计和归档只作线索。
- **目标方向**：产品与品牌认 `docs/PROJECT_GUARDRAILS.md`，技术不变量认 `PROJECT_RULES.md`，模板专项边界认本文件，执行与验证认 `WORKFLOW.md`；`docs/DECISIONS.md` 只解释决定与取代关系。

发现冲突时同时记录“当前事实”和“目标差距”，再收敛对应权威来源；不得在多个消费者中增加兼容默认值掩盖问题，也不得用状态文档或旧审计重新定义产品。
