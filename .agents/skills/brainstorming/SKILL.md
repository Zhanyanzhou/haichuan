# 需求与设计探索

## 目的

只在“直接实现可能得到明显不同的产品结果”时使用本技能。它帮助发现真正需要用户决定的取舍，不把沟通仪式当成设计质量。

## 权限边界

- 权限与审批只认项目 `AGENTS.md`；本技能不能授予或扩大权限。
- 用户明确提出普通、可逆且边界清楚的实现请求，已经构成对该结果的授权；不要在同一结果上追加第二次批准。
- 命中 `AGENTS.md` 的审批项时，先给方案并等待批准；本技能不复制审批域清单。
- 不自动创建提交、推送、删除文件、安装依赖或写入项目外路径。

## 先判断是否需要探索

### 直接实施

满足以下条件时不进入设计流程：

- 用户结果清楚且有可观察验收；
- 现有代码中已有对应流程或模式；
- 实现不会改变业务规则、品牌系统或外部契约；
- 普通实现细节可采用最小合理假设；
- 未命中审批项。

先读相关代码和 diff，然后按 `WORKFLOW.md` 实施与验证。

### 短设计

用户结果明确，但存在一项会影响交互、数据语义、错误恢复或长期维护的真实选择时：

1. 说明当前证据和争议点；
2. 给出推荐方案；只有确有价值时再列一个最强替代方案；
3. 写明影响范围、验收和回退；
4. 只有该选择需要用户取舍或命中审批时才等待确认。

### 可行性调查

用户只要求判断“能否做到”时，先定义问题、证据和停止条件，再做最小只读取证并报告建议。实验代码默认视为临时证据，不自动转成正式实现；需要保留时重新按实现范围判断授权。

### 架构设计

新子系统、新增或实质改变被多个模块依赖的契约、长期数据模型或整体产品流程变更使用完整设计；恢复既有契约一致性的普通 Bug 修复不因此升级。

1. 核对当前结构、事实来源和已有决定；
2. 只询问会改变方案的问题，可一次集中提出少量相关问题；
3. 比较 2–3 个实质方案，明确单一推荐与最强反例；
4. 覆盖组件、数据流、失败路径、迁移、验证和回退；
5. 按审批规则获得确认后，再决定是否需要设计文档和实施计划。

## 设计原则

- 从用户结果、业务事实和失败状态开始，不从想添加的组件开始。
- 复用现有可靠契约，但不要因组件存在就保留不合格的体验。
- 把推断、建议和已核验事实分开；外部或易变化事实需要重新核验。
- 方案越复杂，越要说明复杂度解决了什么已存在的问题。
- 奢侈品前台同时考虑品牌表达、内容真实性、可访问性、性能和运营可维护性；后台优先效率与状态清晰。
- 范围中途扩大或出现高风险证据时暂停升级，不在用户原授权下偷渡新目标。

## 输出

按实际需要输出：结论、证据、推荐方案、最强替代、影响范围、验收、回退和待批准项。任务足够简单时可以只有数段文字；不要强制模板、逐题问答或为“看起来专业”创建文档。
