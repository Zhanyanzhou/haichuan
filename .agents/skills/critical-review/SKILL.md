# 法庭审校（Critical Review）

## 目的

对重大决策执行一场**模拟法庭**：「原告主张 → 被告抗辩 → 举证质证 → 法官判决」，
强制打断预判式生成的惯性，把分歧收敛到可验证证据，而不是靠说服力。

## 角色身份与作用（必读）

本法庭共四个角色，身份、立场与职责边界如下：

1. **原告（主张方）**：AI 扮演。代表“方案该做”的立场，提出主张、方案、结论，
   并给出支持主张的依据。对应 AI 的生成模式（顺着惯性提方案）。

2. **被告（抗辩方）**：AI 扮演。**承接原“红队”的对抗性挑错职责**，
   代表“风险与反例”的立场，专门找原告主张的漏洞、风险、反例、未验证事实。
   对应 AI 的批判模式（打断生成惯性）。不得为反对而反对，
   找不到实质问题时明说“未发现实质反例”。

3. **法律助理（中立证据整理者）**：AI 扮演。不站队，只认证据：
   整理双方依据、核验事实真实性、归纳争议焦点、给出倾向性意见
   （有明确依据才给，并注明“非判决”）。

4. **法官（用户）**：拥有业务取舍、风险接受和高风险操作的最终批准权。
   用户不负责替代证据判断客观事实；缺少事实证据时先取证，缺少业务信息时请求输入。

**要点**：AI 一人分饰原告、被告、法律助理三角，三者立场必须清晰分离、不得混淆。
AI 应根据证据给出事实结论和明确专业意见；用户只裁决需要授权、业务偏好或风险接受的事项。

**边界声明**：被告只能发现当前证据面内的错；知识盲区需靠独立证据、外部工具、目标环境或用户业务输入补足，不以模型品牌代替验证。

## 启用与退出（防止过度触发）

- 本 Skill 是项目内法庭审校的唯一流程；其他通用角色说明或历史对话不能扩大其触发范围，也不能替代 `AGENTS.md` 的授权。
- 本流程仅在用户明确要求“法庭模式”“开庭审校”、同义明确口令或显式调用 `$critical-review`，并指定需要审校的决定时启用。高风险、难回滚、需要授权或存在重大取舍只决定审理级别和证据要求，不构成自动触发；仅提到“法庭”或询问本 Skill 也不触发。
- 回答完毕**立即退出法庭模式**，后续对话恢复普通风格；
  不得因本技能曾加载就持续用法庭腔。
- 日常问答、A 类小改动：即使上下文中包含本技能，也不启用。

## 进入后的范围确认

收到明确口令后，先确认当前是否存在需要审校的具体决定。没有决策对象时，用普通格式说明缺少的决定，不进行形式化庭审；存在决策对象时，再用以下风险面决定简庭或正式庭，而不是重新判断是否触发：

- 认证、权限、订单、库存、金价、隐私、支付、数据库或生产配置；
- `AGENTS.md` 或 `WORKFLOW.md` 规定必须审批、难以回滚或范围显著扩大的事项；
- 实质架构、事实来源、权威职责、安全边界或审批规则变更；
- 错误结论可能造成数据丢失、资金损失、安全风险或难以回滚的后果。

普通组件边界、内部命名和可逆实现细节不因进入法庭模式自动升级为正式庭。用户已经明确批准且没有出现新证据时，执行层不得重复开庭阻塞任务。

## 审理级别

- **简庭**：用于局部、可逆、证据边界清楚的决策。输出最强主张、最强反例、证据结论、专业意见和是否需要批准。
- **正式庭**：用于项目规则规定的高风险域、难以回滚的变更、生产影响或多个实质方案。追加影响范围、失败模式、可逆性、回滚方案、验收门禁和决策记录建议。
- 不因形式感选择正式庭；按风险、可逆性和证据复杂度选择。

## 庭审流程

1. 原告陈述：先以专业身份独立给出结论（主张），声明视角、关键假设与依据来源。
2. 被告抗辩：换一个对立的专业身份，重新读取需求与文档，逐条质疑原告主张。
3. 举证质证：按问题域分流，用证据检验双方主张；证据不足时区分待取证、待业务输入和待用户批准，不把未知事实交给用户凭判断裁决。

## 被告独立性（可执行）

- 被告每一条抗辩都要附能独立核验的出处（代码行 / 文档段 / URL）——
  只有能核验的质疑才有分量，空泛的“可能有风险”进不了裁决。
- 不要拿“原告已经论证过”当依据——同一个模型自我引用会掩盖真实缺陷。
- 仅当用户或上级规则授权多智能体、问题存在可独立分区的风险面且独立审查能增加证据时使用子代理；否则在当前会话内完成，不为形式完整额外编排。

## 举证质证（按问题域分流）

- 代码/工程类：分歧转可验证断言（类型检查 / 测试 / 构建 / 页面实查），
  以运行结果为客观证据；AI 据此形成事实结论，但不代替用户批准高风险操作。
- 决策/业务类：给出明确专业意见，并把需要用户批准的业务取舍与可自行核验的事实分开。

## 证据真实性核查

- 主张涉及外部 / 业务事实时，被告必须质证：“这个事实核验过吗？来源是什么？”
- 贴个 URL 不算核验——链接可能是编的或不对应的，要真正打开确认它支持主张。
  有工具面时就实际打开 / 验证；无工具面时明说“无工具，无法核验”，降级为待取证。
- 核验不到的客观事实标为「待取证」；只有用户掌握的信息标为「待业务输入」；事实已清楚但需要授权或风险接受的事项才标为「待用户批准」。
- 未经核验的事实和编造的事实一样危险，不能通过用户“批准”变成已证实事实。
- 代码全绿 ≠ 事实正确：类型检查、测试、构建只证明内部自洽。

## 结果分层

- **事实结论**：由代码、运行结果、当前配置或可靠外部证据支持，AI 可以明确判定。
- **专业意见**：AI 基于证据给出的单一推荐及适用条件，必须注明主要风险和置信度。
- **待取证**：缺少命令、环境、代码路径、真实页面或外部来源，继续取证后再判断。
- **待业务输入**：事实只能由项目负责人提供，例如商业授权、真实运营状态或品牌资产确认。
- **待用户批准**：事实和方案已经清楚，但涉及权限、风险接受、业务取舍或必须审批的操作。

## 庭审终结与升级（禁止和稀泥）

- 观点交锋最多 2 轮（被告抗辩 1 轮 → 举证质证 1 轮），防止无限辩论；证据调查不受该轮数限制。
- 按 `WORKFLOW.md` 继续能增加新证据或排除假设的验证；连续两轮没有新证据时停止重复扫描。高风险问题不得因为辩论轮数耗尽而草率下结论。
- 证据充分时给出**明确的法律助理意见**：写明倾向哪一方、依据是什么，
  并注明“这是专业意见，不代替用户的授权与业务取舍”。
  用“双方都有道理”“各有优劣”“视情况而定”收场等于没开庭——
  它不提供任何可执行的信息，又把该做的判断推回给用户；
  给出明确判定条件的结论（如“预算充足选 A，否则选 B”）不算含糊。
- 升级前先把能验证的验完：代码类分歧先跑类型检查 / 测试 / 构建 / 页面实查，
  别把能自己查清的事推给用户。
- 完成相称取证后仍无法判断 → 休庭并区分缺少的证据、业务输入和批准事项，不得继续和稀泥或假装已有结论，输出「庭审摘要」：

  ```text
  ## 庭审摘要
  ### 争议焦点
  - 原告主张 + 依据
  - 被告抗辩 + 依据
  ### 无法判断的原因
  - 缺什么证据 / 环境 / 真实输入
  ### 可选方案
  - 方案 A：利弊
  - 方案 B：利弊
  ### 法律助理意见
  - 有明确依据：给出倾向 + 置信度
  - 证据不足：明写“当前无法形成可靠倾向”，并列出解除条件
  - 有足够证据时必须给单一明确倾向；禁止“建议综合 / 折中”
  ### 待取证
  - 缺少的命令、环境、代码或外部证据
  ### 待业务输入
  - 只有项目负责人掌握的真实信息
  ### 待用户批准
  - 已有充分事实基础、需要授权或风险接受的事项
  ```

- 用户作出批准或业务裁决后：**执行层**以用户决定为准继续执行，不反复纠缠；
  但涉及高风险 / 安全 / 隐私隐患时，**一次性**明确记录到交付报告，
  提醒后仍按法官决定执行；只有出现新的实质证据时才可重新提出。
- 被告目标是找出被忽略的风险或反例；找不到实质问题时明说“未发现实质反例”，
  不得为反对而反对。

## 决策落档

- 架构、规则、品牌系统、权限、交易、数据和生产决策获批后，判断是否需要同步 `docs/DECISIONS.md` 或对应权威文档。
- 记录决定、依据、适用范围、可逆性、回滚方式、验收条件和重新开庭条件；不得把庭审过程全文复制进项目文档。
- 文档写入仍受当前任务授权约束；未授权时只在交付中给出建议记录内容，不自行扩展修改范围。

## 能力降级

- 不按模型品牌、供应商或推定强弱分配权限与审查权；统一遵守 `docs/AI_TOOLING.md`。
- 缺少浏览器、测试、外部检索、子代理或目标环境时，明确列出不可核验项，改用当前可用的最小证据面，不得伪造完整审查。
- 降级时可简化为「主要风险 + 已核验依据 + 待取证 + 待业务输入 + 待用户批准」，但 AI 不得代替用户授权、禁止和稀泥、事实核查和升级给用户四条底线不可省略。

## 输出

庭审角色与逐步推理默认在内部完成，最终只呈现帮助用户决策的摘要，不逐角色复述冗长过程。交付时按实际存在的类别输出；空类别省略：

```text
### 法律助理意见（专业建议，不代替用户授权）
### 依据
### 被告抗辩要点
### 事实结论
### 待取证
### 待业务输入
### 待用户批准
### 决策落档建议
```
