# 系统化调试

## 目标

先以证据定位原因，再选择最小完整修复，避免靠连续猜测叠加补丁。调试深度由未知程度、风险、可逆性和跨模块影响决定，而非由“这是 Bug”自动决定。

## 权限与安全

- 读写、诊断命令、插桩、Git、环境、数据库和生产操作仍遵守 `AGENTS.md`。
- 不通过打印环境变量、密钥、令牌、客户信息或完整第三方响应取证。需要观察边界数据时只记录最小、脱敏且当前任务必要的信息。
- 不为了复现而破坏真实数据、生产状态或用户已有改动；无法安全复现时明确证据缺口。

## 先选调查深度

### 短路径

适用于错误信息、调用链和触发条件已足以定位的局部问题：

1. 读取错误、相关 diff 和最小调用链；
2. 写下可核验的原因假设；
3. 在根因或共享入口做最小修复；
4. 运行能证明该行为的目标检查，并按 `verification-before-completion` 限定结论。

### 完整调查

原因不明、跨前后端/服务/数据库边界、间歇性、并发、性能、权限、数据风险，或两次不同假设都未增加证据时：

1. **定位症状**：收集可重复步骤、错误、时间条件、受影响范围和近期相关改动；
2. **追踪路径**：从异常值、状态或副作用向上游追到来源，必要时读取 `root-cause-tracing.md`；
3. **比较模式**：核对同仓库可工作的相似路径、合同、配置与失败条件；
4. **验证假设**：一次只验证一个可证伪假设，优先使用只读检查、目标测试或安全的临时观察；
5. **实施与回归**：修复根因，验证原症状、受影响边界和必要回归。

诊断插桩只在已有证据不足且能安全增加信息时使用。临时插桩不应成为正式功能；保留它需要说明长期价值并按实施范围处理。

## 修复与验证

- 优先修根因和共享入口，不在多个调用方堆症状补丁。
- 修复 Bug 时优先留下可复现原症状且修复后通过的目标检查；无法安全建立自动化回归时，说明原因并使用最强可用的重复检查。
- 不把“先让测试失败”当作每个修复的硬门槛，更不能通过回退用户工作、触碰真实数据或制造破坏性状态来证明失败。
- 每次尝试必须增加证据或排除假设。两次没有新增信息时停止盲目修改，回到取证或请求缺失的业务/环境信息。
- 多次修复仍不能收敛时，检查是否存在共享状态、错误边界、契约或架构问题；只有需要改变架构或命中审批项时才暂停提交方案，不按失败次数自动判定架构错误。

## 输出

按实际存在的内容说明：症状与范围、已核验原因、修复点、验证结果、未覆盖边界和待确认项。证据不足时明确写“待取证”，不得把猜测包装成根因。
